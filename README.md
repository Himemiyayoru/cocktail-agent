# Bob's Special Blend

A cocktail discovery and recipe-adjustment app built with Expo, React Native, and FastAPI. The main task is to move from **ingredients you have → a feasible recipe → a deliberate adjustment → a saved version**.

## Main flow

1. **My Cabinet:** search the ingredient list and record what you own. Matching separates complete recipes from recipes missing one or two ingredients, with owned and missing counts. Empty or unrelated inventories do not produce “almost ready” results.
2. **Recipe Studio:** review the original amounts, substitute an ingredient, and compare estimated alcohol, sugar, and appearance. Each ingredient slot keeps its own amount, even when two slots use the same ingredient.
3. **Choose a glass:** changing glassware preserves the recipe. If the amounts exceed its nominal capacity, an explicit scaling action adjusts all amounts proportionally.
4. **Save a version:** name and save your adjusted ingredients, amounts, glass, and display mode. Reopen it from **Saved → Your versions**, or reset the editor to the original recipe. Recipe favorites remain separate from customized versions.
5. **Ask Bob:** optionally restrict recommendations to complete recipes from your cabinet. Empty or incomplete cabinets receive a next-step message without an AI call. Voice input is transcribed into editable text.

## Runtime architecture

- **`mobile/`:** Expo SDK 54, React Native, Expo Router, and TypeScript. A bundled recipe index supports browsing and search. The recipe screen calculates its visual estimates locally. Cabinet contents, favorites, and saved versions use device-local AsyncStorage.
- **`backend/api/main.py`:** FastAPI serves recipe details, ingredient categories, matching, substitutes, chat, and transcription. It loads `backend/data/FINAL_COCKTAIL_PHYSICS_DB.json` into memory at startup.
- **`backend/api/recommendations.py`:** deterministic inventory normalization, matching, substitution ranking, and exact candidate validation. Substitution ranking uses category and physical estimates; it is not generated by an LLM.
- **Cloud AI:** chat uses Groq's OpenAI-compatible API; transcription uses OpenAI's `whisper-1` API. Both are optional. Catalog, matching, and substitution endpoints work without AI credentials.

`backend/database.py` and seed scripts are retained tooling. The running API reads the JSON recipe catalog and stores subscription access and AI usage in a separate SQLite billing ledger. No local Ollama or Whisper installation is needed for the current API.

## Local setup

The current development environment uses Python 3.12 and Node.js 24 with npm. The mobile tests import TypeScript directly and need Node's built-in TypeScript support.

From the repository root, using PowerShell:

```powershell
# First-time environment setup
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend/requirements.txt

# Start the local API
python -m uvicorn backend.api.main:app --host 0.0.0.0 --port 8000 --reload
```

Optional backend environment variables, supplied through your shell or a local `.env` file:

- `GROQ_API_KEY`: enables Bob's chat.
- `GROQ_MODEL`: overrides the configured default, `openai/gpt-oss-20b`.
- `OPENAI_API_KEY`: enables cloud voice transcription.

Keep credentials out of source control and the mobile app. Missing keys produce a recoverable 503 response from the relevant AI endpoint.

In another terminal:

```powershell
cd mobile
npm install
$env:EXPO_PUBLIC_API_URL = 'http://127.0.0.1:8000'
npm run web
```

For a physical phone, set `EXPO_PUBLIC_API_URL` to your development computer's reachable LAN address, then run `npm start`. The phone's `localhost` refers to the phone itself. Use a compatible native development build for subscriptions; Expo Go does not include the required in-app purchase module.

`EXPO_PUBLIC_API_URL` is a public configuration value, never a secret. Set it explicitly when checking local backend changes; if omitted, `mobile/src/lib/api.ts` uses its configured hosted fallback. Restart Expo after changing this value.

The splash screen includes both Expo native configuration and an in-app startup overlay. Changes to the native splash in `mobile/app.json` require rebuilding and reinstalling the native app; a JavaScript refresh alone does not update it. Check the native result in a rebuilt development or release binary.

## Verification

Run mobile checks from `mobile/`:

```powershell
npm test
npm run typecheck
```

Run backend checks from the repository root in the Python environment:

```powershell
# TestClient's HTTP transport is a test dependency, separate from runtime requirements.
python -m pip install httpx
python -B -m unittest discover -s backend/tests -v
```

The backend suite substitutes fixture recipes, disables dotenv loading, and mocks AI calls. It does not require real credentials or make AI requests. The tests cover matching boundaries, candidate validation, API compatibility, unavailable AI services, and substitution ordering. Mobile tests cover recipe state, persistence, cabinet filtering, and request failures.

Also walk through the app: edit a cabinet, inspect a missing-ingredient result, swap to an ingredient already in another slot, select a smaller glass, explicitly scale, save, and reopen the version. Check loading, retry, and storage-error states on the target device.

## Limits and evidence

- The cabinet tracks ingredient presence, not remaining quantities or equipment. A complete ingredient match does not verify that enough stock is available.
- Alcohol, sugar, color, and capacity displays are estimates based on stored baselines. They are not laboratory measurements or guarantees of flavor equivalence. Ice, dilution, brands, and preparation can change the result; leave serving space accordingly.
- Saved data stays on the device or browser. There is no account or cross-device synchronization.
- AI features require network access and configured provider keys. Text and audio submitted to these features are sent to their respective cloud providers.
- Automated checks establish software behavior. They are not usability research, taste testing, or evidence of improved user outcomes. Portfolio claims about usability need observed sessions and documented iterations.

### Bob subscription and monthly AI allowance

The store product `bob_monthly` costs USD 4.99 per month. Configure that price and
monthly billing period in App Store Connect / Google Play Console. The server
shares a USD 4.00 allowance between Bob chat and voice in each verified subscription
period. It reserves the maximum request cost before calling the provider, disables
provider retries, and keeps reservations after ambiguous network failures. Such
failures can conservatively reduce the available allowance even without a reply.
Chat is settled from provider token usage; voice is decoded to bounded PCM (120
seconds maximum) and charged at USD 0.006/minute, rounding seconds upward.

Install `backend/requirements.txt` (including PyAV). Set `BOB_BILLING_DB` to a
SQLite file on a **persistent disk** and set a stable `BILLING_TOKEN_SECRET` on the
server. All processes must share this database; separate instances with separate
disks do not enforce a shared allowance. Ephemeral Render storage would lose usage
on deployment. Keep provider price settings current if the model or prices change.
Store verification also requires the Apple root certificate (`APPLE_ROOT_CA_PATH`)
and/or `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`, with matching application identifiers.
Use a native development/release build for in-app purchases, not Expo Go.

Recipe detail screens use the bundled catalog, including on first offline open.
After changing the backend catalog, run `npm run sync-recipes` in `mobile` and
ship the updated mobile bundle together with the backend catalog. IDs remain the
catalog array indices, so avoid reordering existing recipes.


## Render deployment

The repository includes `render.yaml` for a single Python web service with a
1 GB persistent disk. Apply it to the existing `bobs-special-blend` service in
its current workspace. Verify the existing service identity before applying a
Blueprint; do not accidentally create a second production service. The disk
requires a paid instance. Review the current instance and disk prices in Render.

For an existing service configured through the dashboard, use these settings:

- Root directory: `backend` (matches the existing service).
- Build command: `pip install -r requirements.txt`.
- Start command: `uvicorn api.main:app --host 0.0.0.0 --port $PORT --workers 1`.
- Disk name: `bob-billing`; mount path: `/var/data`; size: `1 GB`.
- `BOB_BILLING_DB=/var/data/bob_billing.sqlite`.
- `BOB_BILLING_MOUNT=/var/data`.
- Health check path: `/health`.

Keep existing provider and store credentials. If `BILLING_TOKEN_SECRET` already
exists, preserve its value. Otherwise the server generates a signing key once
and stores it in the persistent database. Do not rotate it during a deployment.
On Render, the billing code refuses to use an unmounted disk or a database path
outside the mount. A failed storage health check returns HTTP 503.

Before the first disk deployment, check whether the current instance already
contains billing records. If it does, export the database using SQLite's backup
API before restarting that instance. Preserve the signing key along with the
ledger, then restore the backup onto the new disk before accepting paid traffic.
Do not overwrite an existing production database with a local development file.

After deployment, verify that `/health` reports `status: ok`,
`billing_storage: ready`, and the expected Git commit. Verify that an
unauthenticated request to `/api/v2/chat_with_bob` returns HTTP 401. To confirm
persistence, record a checksum of a SQLite backup and the ledger row counts,
restart the service, and compare them again while paid traffic is paused.
Attaching a disk can briefly interrupt service during deployments.

Pushing `render.yaml` to GitHub alone does not attach the disk: the Blueprint
must be applied, or the existing service must be updated in the Render dashboard.
The mobile application must be rebuilt separately to include the native purchase
module and bundled recipe details.
